## Step 8 — Cloud Run

### Decision: consumers on worker pools
The worker and the sweeper pull from RabbitMQ and serve no HTTP, so they run as **Cloud Run worker pools** (`google_cloud_run_v2_worker_pool`, GA in google provider 8.4.0, available in `us-central1`), manual scaling, 1 instance each. Rejected: a service with `min-instances=1` + always-on CPU (needs a fake health port, bills the same) and a scheduled job for the sweeper (cheaper, but two patterns for two consumers).

### Blocker found before deploying: the MCP host allowlist (`17831b7`)
The MCP SDK's DNS-rebinding protection only accepted `127.0.0.1:*`, `localhost:*`, `[::1]:*` and `mcp_server:*`, hardcoded in `mcp_server.py`. On Cloud Run the `Host` header is `mcp-server-<project-number>.us-central1.run.app`, so every worker request would have gotten a 421 (the same bug Phase 1.C hit with the compose hostname).
- Fix: `src/mcp_server/security/transport.py` builds the allowlist from the defaults plus `MCP_ALLOWED_HOSTS` (comma-separated). Extra hosts are added **exactly**: Cloud Run's `Host` carries no port, and the SDK's `host:*` pattern only matches `host:<port>`. Their origins are `https://<host>`. The protection stays on.
- TDD: 5 unit tests (`tests/unit/security/test_transport.py`) + 2 integration tests (configured host accepted, unconfigured host → 421). The SDK sends the 421 and then raises; the test transport uses `raise_app_exceptions=False` to keep the response, as uvicorn does.
- 255 tests pass; `ruff check src tests` and `mypy --strict src` clean. Image `mcp_server:17831b7` built, checked inside the container, pushed.

### What was deployed (`infra/cloudrun.tf`)
| Resource | Type | SA | Notes |
|---|---|---|---|
| `mcp-server` | service, public | `mcp-server-sa` | `max-instances=1` (SSE stream + POSTs on one instance); `mcp-clients-json` mounted at `/secrets/mcp_clients.json` via `MCP_CLIENTS_FILE`; `MCP_ALLOWED_HOSTS` = its deterministic host |
| `gateway` | service, public | `gateway-sa` | port 8000, `max-instances=2` (caps a flood of claims); `MCP_SERVER_URL` for the health ping |
| `worker` | worker pool | `worker-sa` | `LLM_PROVIDER=vertex`, `VERTEX_PROJECT`, `GROQ_API_KEY` + `MCP_CLIENT_TOKEN` from secrets, 1 vCPU / 512 Mi |
| `sweeper` | worker pool | `sweeper-sa` | worker image with `command = python -m src.worker.recovery_sweeper` |
| `dashboard` | service, public | `dashboard-sa` (no roles) | port 8501, `session_affinity` (Streamlit websocket), `GATEWAY_URL` = gateway's deterministic URL |

- **Why the MCP server is `allUsers` at the Cloud Run layer:** Cloud Run IAM reads the `Authorization` header, which the worker already uses for its Phase 1.B bearer token. The Phase 1.B boundary does the real auth.
- **Deterministic URLs:** `<service>-993240087609.us-central1.run.app`. Only this form is in `MCP_ALLOWED_HOSTS`; the legacy `*-ljm5hefnsq-uc.a.run.app` form would get a 421 on the MCP server.
- **Perpetual diff found in review:** Cloud Run stores the MCP server's volumes as `mcp-clients` then `cloudsql`; with the `.tf` in the other order every plan showed a reorder (a new revision per apply). Fixed by matching the stored order.
