# MCP Security Boundary (Phase 1.B)

**Status:** In progress. This document is the specification for Phase 1.B; the implementation follows it, and each guarantee below is mapped to the test that verifies it.

---

## 1. Purpose

The central architectural claim of this project is that the MCP server is the only path from the LLM to side-effecting operations (`execute_refund`, `validate_fraud_score`). That claim holds only if the server itself enforces who may call what, with which arguments, how often, and leaves a record of every attempt.

This document specifies that enforcement: the threat model it responds to, the order in which checks run, the data it persists, how each failure is reported, and what remains out of scope.

---

## 2. Current State

| Control | State | Detail |
|---|---|---|
| Client authentication | Not implemented | HTTP/SSE endpoints on port 8080 accept any connection. |
| Per-tool authorization | Not implemented | Every connected client can list and call every tool. |
| Argument validation | Partial | Types inferred from Python type hints (`amount: float`); no ranges, limits, or enums. |
| Rate limiting | Not implemented | A looping agent can call `execute_refund` without bound. |
| Audit log | Not implemented | Console logs from Uvicorn and final transaction state only; no record of who called which tool with which arguments. |

Consequence: any process with network access to the MCP server can execute refunds directly, bypassing the agent, the LLM-as-a-Judge, and the Phase 2 rule base.

---

## 3. Threat Model

### 3.1 Assets

- **Side-effecting tools:** `execute_refund` moves money; `validate_fraud_score` influences whether money moves.
- **Audit trail:** the only record that lets an approval be reconstructed after the fact.
- **Client credentials:** each worker's token.

### 3.2 Actors and scenarios

| # | Actor | Scenario | Before 1.B | After 1.B |
|---|---|---|---|---|
| T1 | Process inside the network, no credentials | Calls `execute_refund` directly on port 8080 | Succeeds | Rejected at connection (401); no tool reachable |
| T2 | Legitimate worker with the wrong role | A worker that should only score fraud calls `execute_refund` | Succeeds | Tool not listed for that identity; call denied and audited |
| T3 | Agent in a loop | The LLM repeats a tool call many times per second | Every call executes | Throttled per identity and tool; excess calls rejected and audited |
| T4 | Malformed or hostile arguments | Negative amount, amount above policy, unknown currency, extra fields | Executes if types coerce | Rejected by server-side schema and audited |
| T5 | Poisoned retrieved document | A document in the RAG corpus instructs the agent to call a tool it should not use | Succeeds if the tool exists | Denied if outside the identity's allowlist (see Section 6) |
| T6 | After-the-fact dispute | Someone needs to know who triggered a refund and with what arguments | No record | Reconstructable from the audit table |

### 3.3 Assumptions

- The PostgreSQL superuser and the host running the services are trusted.
- Tokens are high-entropy random values generated by the operator, not user-chosen passwords.
- Workers keep their own token confidential.

### 3.4 Out of scope

- Traffic interception between services (no TLS yet).
- Credential rotation, expiry, and secret management.
- Compromise of the host, the container runtime, or the database superuser.
- Attacks on the model provider.
- The agent choosing a wrong but *authorized* tool or argument within limits. This residual risk is constrained by the LLM-as-a-Judge and the Phase 2 rule base, not by this layer.

## 4. Request Pipeline

Authentication happens once per connection. Every tool call on that connection then passes through the same ordered checks:

```
connection ──► [1] authenticate token ──► client_id bound to session
                     │ fail: 401, connection refused
                     ▼
tool call ───► [2] authorize (client_id, tool)
                     │ fail: denied
                     ▼
               [3] rate limit (client_id, tool)
                     │ fail: rate_limited
                     ▼
               [4] validate arguments (Pydantic)
                     │ fail: invalid
                     ▼
               [5] write decision row (allowed) ──── fail: tool not executed
                     ▼
               [6] execute tool
                     ▼
               [7] write result row
```

Every outcome of steps 2–4 also writes a decision row before the error is returned.

**Why this order**

1. **Authentication first.** Without an identity, no later check has anything to evaluate. It is also the cheapest check and rejects anonymous traffic before any database access.
2. **Authorization before validation.** A caller without permission for a tool should learn nothing about that tool's argument schema from validation errors.
3. **Rate limiting before validation.** A looping agent that keeps sending malformed arguments must still be throttled. Invalid attempts count toward the limit.
4. **Audit before execution.** The decision row is written before the tool runs, so no execution can happen without a record. If that write fails, the tool does not run.

## 5. Controls

### 5.1 Authentication

- Each client (worker type) has its own token. There is no shared server-wide key, because a shared key authenticates "someone with the key" and makes per-identity authorization impossible.
- Tokens are generated by the operator with `secrets.token_urlsafe(32)` or equivalent.
- The server stores only the SHA-256 hash of each token. Because tokens are high-entropy random values rather than passwords, an unsalted fast hash is sufficient; a leaked registry file does not reveal usable tokens.
- The client sends `Authorization: Bearer <token>` when opening the SSE connection.
- The server hashes the presented token and compares it against the registry with `hmac.compare_digest`.
- `client_id` is derived from the matched registry entry. It is never read from a caller-supplied header or argument.
- The resolved `client_id` is bound to the session and propagated to tool handlers through a context variable.

**Client registry** (`MCP_CLIENTS_FILE`):

```yaml
clients:
  - client_id: refund-worker
    token_sha256: "<hex digest>"
    tools:
      execute_refund:
        rate_limit_per_min: 10
      validate_fraud_score: {}
  - client_id: fraud-worker
    token_sha256: "<hex digest>"
    tools:
      validate_fraud_score: {}
```

A tool absent from a client's `tools` map is not allowed for that client. An empty `{}` entry means allowed with the default rate limit.

### 5.2 Authorization

- `list_tools` returns only the tools in the caller's allowlist. A client does not see tools it cannot use.
- `call_tool` for a tool outside the allowlist is rejected with decision `denied` and audited.
- The allowlist is read only from the registry on the server. No part of the request (prompt text, retrieved documents, tool arguments, headers other than the token) can change it.

### 5.3 Argument validation

Every tool takes a Pydantic model as its input, validated on the server regardless of what the LLM serialized.

- `model_config = ConfigDict(extra="forbid")`: unknown fields are rejected, not ignored.
- `execute_refund`:
  - `amount`: `Field(gt=0, le=settings.REFUND_MAX_AMOUNT)`
  - `currency`: enum (`USD`, `EUR`, `ARS`)
  - `transaction_id`: constrained format (pattern defined by the transaction model)
- `validate_fraud_score`: equivalent constraints on its own arguments.
- Fields containing personal data are marked in the model (`json_schema_extra={"pii": True}`) so the audit layer can mask them without per-tool code.

Validation failures return decision `invalid` with the field-level errors, and are audited.

Validation here enforces **policy bounds**, not business correctness. Whether a refund is warranted is decided upstream by the judge and the rule base; this layer guarantees that even a wrongly approved call cannot exceed hard limits.

### 5.4 Rate limiting

- Scope: per `(client_id, tool)`.
- Window: sliding 60 seconds.
- Limit: `rate_limit_per_min` from the registry entry, falling back to `MCP_RATE_LIMIT_PER_MIN`.
- Source of truth: count of decision rows in `mcp_audit_log` for that client and tool within the window, regardless of decision. Denied and invalid attempts count.
- Exceeded: decision `rate_limited`, audited.

Counting in PostgreSQL rather than in process memory means the limit holds across multiple MCP server replicas, which the HTTP/SSE transport decision explicitly allows for, without adding Redis.

**Known imprecision:** concurrent calls arriving at the same moment near the limit can each read the same count and all pass, overshooting by up to the number of concurrent in-flight calls. At this system's call volume that is acceptable; a strict limit would require a row lock or an atomic counter.

### 5.5 Audit log

Every tool call attempt produces at least one row. The table is append-only for the MCP service. Schema and permissions are in Section 7.

## 6. Prompt-Injection Invariant

Retrieved documents are untrusted input: anyone who can place content in the RAG corpus can place instructions in front of the model. Detecting injected instructions by content is heuristic and can be evaded. This layer instead guarantees a structural property:

> **The set of tools available to a request is determined by the caller's authenticated identity on the server. Nothing in the prompt, in retrieved documents, or in tool arguments can extend it.**

**What it guarantees:** an injected instruction cannot cause a worker to execute a tool outside its role. A document instructing the fraud worker to issue a refund produces a denied, audited call, because `execute_refund` does not exist for `fraud-worker`.

**What it does not guarantee:** an injected instruction can still influence which *allowed* tool the agent calls and with what arguments. For `refund-worker`, a poisoned document could push the agent toward an unwarranted refund. That residual risk is bounded by:

- hard argument limits (Section 5.3), which cap the damage of any single call;
- rate limits (Section 5.4), which cap repetition;
- the LLM-as-a-Judge and the Phase 2 rule base, which must both approve before a refund executes;
- the audit trail, which makes every such call visible and attributable.

The design consequence is least privilege at the worker level: tools should be split across identities so that no single worker holds more side-effecting capability than its task needs.

## 7. Audit Table

### 7.1 Schema

`mcp_audit_log`, created by an Alembic migration.

| Column | Type | Notes |
|---|---|---|
| `id` | `BIGSERIAL` | Primary key |
| `invocation_id` | `UUID` | Shared by the decision row and the result row of one call |
| `event_type` | `TEXT` | `decision` or `result` |
| `timestamp` | `TIMESTAMPTZ` | Server time, `now()` default |
| `client_id` | `TEXT` | From the registry; never null, because unauthenticated connections never reach a tool |
| `tool_name` | `TEXT` | |
| `arguments` | `JSONB` | PII fields masked (Section 5.3) |
| `decision` | `TEXT` | Decision rows: `allowed`, `denied`, `invalid`, `rate_limited` |
| `result_status` | `TEXT` | Result rows: `success`, `error` |
| `error_detail` | `TEXT` | Validation errors or tool exception class |
| `duration_ms` | `INTEGER` | Result rows: tool execution time |

Index: `(client_id, tool_name, timestamp)` for the rate-limit query.

### 7.2 Why two rows per call, not one

A single row with `result_status` filled in after execution would require `UPDATE`, which the MCP service role is not granted. Writing the decision and the result as separate events keeps the table strictly insert-only.

It also makes one failure mode detectable: an `allowed` decision row with no matching result row means the process died between execution and recording. Those calls have an unknown outcome and can be found with a single query:

```sql
SELECT d.*
FROM mcp_audit_log d
LEFT JOIN mcp_audit_log r
  ON r.invocation_id = d.invocation_id AND r.event_type = 'result'
WHERE d.event_type = 'decision'
  AND d.decision = 'allowed'
  AND r.id IS NULL;
```

Recovery from that state relies on the worker's idempotency guarantee on `request_id`, not on this layer.

### 7.3 Permissions

The migration creates a role `mcp_service`, used only by the MCP server:

```sql
GRANT INSERT, SELECT ON mcp_audit_log TO mcp_service;
GRANT USAGE ON SEQUENCE mcp_audit_log_id_seq TO mcp_service;
-- No UPDATE, no DELETE, no TRUNCATE.
```

This protects the log against the MCP service itself, including a compromised MCP process. It does not protect against the database superuser (Section 3.4).

## 8. Failure Semantics

Authentication fails at the HTTP layer, before an MCP session exists. After that, tool calls travel as JSON-RPC messages over an established session, so per-call rejections are returned as MCP error results carrying the decision, not as separate HTTP status codes.

| Check | Response | Audited | Counts toward rate limit |
|---|---|---|---|
| Missing or invalid token | HTTP 401, connection refused | No (no identity, no session) | No |
| Tool not in allowlist | MCP error, decision `denied` | Yes | Yes |
| Rate limit exceeded | MCP error, decision `rate_limited` | Yes | Yes |
| Argument validation failed | MCP error, decision `invalid`, field errors | Yes | Yes |
| Decision row write failed | MCP error, tool not executed | No (the write is what failed; logged to stderr) | No |
| Tool raised an exception | MCP error, result row `error` | Yes | Yes (via decision row) |
| Result row write failed | Tool result returned; outcome logged to stderr | Decision row only; detectable via Section 7.2 query | Yes |

**Fail closed:** every failure before execution means the tool does not run. The only case where a tool runs without a complete record is a failure after execution, and that case is detectable.

## 10. Verification

Each guarantee maps to at least one test. Unit tests live in `tests/unit/security/`; integration tests run against real PostgreSQL in `tests/integration/`.

| Guarantee | Test |
|---|---|
| No token → no access | Connect without `Authorization`; expect 401 |
| Invalid token → no access | Connect with a random token; expect 401 |
| Identity comes from the token only | Valid token plus a spoofed `client_id` header; audit row shows the registry identity |
| Tool listing is filtered | `fraud-worker` lists tools; `execute_refund` absent |
| Non-allowed call is denied | `fraud-worker` calls `execute_refund`; decision `denied`, row present |
| Amount bounds | `amount=0`, `amount=-1`, `amount=REFUND_MAX_AMOUNT+1`; all `invalid` |
| Currency enum | `currency="XXX"`; `invalid` |
| Extra fields rejected | Unknown argument; `invalid` |
| PII masked | Call with a PII-marked field; stored argument is masked |
| Rate limit | Limit + 1 calls within 60 s; last one `rate_limited` |
| Invalid attempts are throttled | Limit + 1 invalid calls; last one `rate_limited` |
| Fail closed on audit failure | Force the decision-row insert to fail; tool handler never invoked |
| Insert-only role | As `mcp_service`, attempt `UPDATE` and `DELETE`; both rejected by PostgreSQL |
| Unknown-outcome detection | Kill between execution and result write; Section 7.2 query returns the call |
| Prompt-injection invariant | Seed a document instructing a refund; process it as `fraud-worker`; decision `denied`, no refund executed |

The prompt-injection test is also added to the failure injection suite ([Failure Injection Tests](../testing/chaos_engineering_armageddon.md)).

## 11. Limitations and Future Work

| Limitation | Effect | Path forward |
|---|---|---|
| No TLS between services | Tokens and arguments travel in plain text on the internal network | TLS termination per service, or mTLS through a service mesh |
| Static tokens, no expiry | A leaked token is valid until the registry is edited | Short-lived signed tokens (JWT) issued per worker, or mTLS client certificates |
| Registry in a file | Changes require a restart or reload | Registry table in PostgreSQL with a reload signal |
| Superuser can alter the audit table | Log is tamper-resistant against the service, not the host | Hash chain across rows, or shipping rows to write-once external storage |
| Rate-limit overshoot under concurrency | Up to N in-flight calls can exceed the limit | Row lock or atomic counter per `(client_id, tool)` |
| Validation enforces bounds, not correctness | A wrong refund within limits passes this layer | Handled by the judge and the Phase 2 rule base, by design |
